# Набросок мультиплеера

Сетевой игры пока нет. Это черновик: что уже готово, чего не хватает, как устроить обмен и в каком
порядке это делать. Правила игры при этом не меняются — меняется только то, кто и когда ими управляет.

## 1. Что уже позволяет включить сеть

| Свойство | Где | Почему важно для сети |
|---|---|---|
| Ядро правил без Unity | `Assets/Scripts/Mahjong/Rules` | тот же код крутится на сервере (консоль/headless) и в редакторе |
| Ход описывается одним объектом | `LegalAction`, `GameState.GetLegalActions` | сервер может проверить любой ход клиента: он либо есть в списке, либо это подделка |
| `GameState.Apply(action)` | `Rules/GameState.cs` | одно место, где состояние меняется; всё остальное — проекция |
| Раздача детерминирована по сиду | `GameState.StartHand(dealer, seed, roundWind)` | реплей и догон таблицы без пересылки стены |
| Заявки имеют порядок | `Rules/ClaimPriority.cs` | окно заявок разрешается одинаково на всех столах |
| Время вне движка | `Controls/PlayClock.cs`, `Controls/ClockExpiry.cs` | таймер можно вести на сервере и не зависеть от часов клиента |
| Штрафы и судья | `Rules/Penalties.cs` | есть чем обслужить спорное решение без переписывания хода |
| Итоги сессии | `Rules/GameSession.cs` | таблица считается на сервере, клиент её только показывает |

## 2. Чего не хватает

1. **Скрытая информация.** Сейчас `GameState` целиком открыт вызывающему: в нём закрытые кости всех
   игроков. Нужна проекция на место (seat view): свои закрытые кости и комбинации, у соперников —
   только число закрытых костей, открытые комбинации, сбросы, число костей в стене, чей ход и фаза.
2. **Протокол.** Нужен формат хода: тип, кость (по `InstanceId`), требуемые кости. Строковый код хода
   годится и для сети, и для логов, и для реплеев.
3. **Проверка и отказ.** Сервер обязан отвечать «хода нет в списке допустимых» и ничего не менять.
4. **Транспорт.** Ядру всё равно, TCP это или WebSocket; нужен интерфейс и реализация «в процессе»
   для тестов и для того же прототипа без сети.
5. **Серверные часы.** Окна 20 / 10 / 3 секунды ведёт сервер, клиент показывает остаток по отметке
   времени сервера, а не по своим часам.
6. **Переподключение.** Снимок проекции + лог применённых ходов; лог переигрывается с сида.
7. **Порядок событий.** Клиенту нужна не только проекция, но и «что произошло»: добор, снос,
   объявление, замена цветка, конец руки — иначе анимация невозможна.

## 3. Архитектура (авторитарный сервер)

```
клиент A ──┐                            ┌── Rules/GameState  (единственный источник истины)
клиент B ──┼── транспорт ── AuthoritativeTable ── │
клиент C ──┤                            └── GameSession (раунд, часы, штрафы, таблица)
боты/D   ──┘
```

- Клиент рисует только то, что пришло в проекции, и отправляет намерение: `discard:17`, `pung:17`.
- Сервер проверяет намерение через `GetLegalActions`, применяет через `Apply` и рассылает события.
- Никакой клиентской логики правил: всё, что клиент «знает», приходит от сервера (иначе два клиента
  разойдутся в спорной руке вроде ограбления конга).
- Боты — такие же места, что и люди: `IMahjongBot` вызывается на сервере, разница только в том,
  что ответ приходит сразу, а не по сети.

## 4. Сообщения

Формат — строки ASCII, разделитель `|`; в JSON переводится один в один, когда появится удобный
сериализатор. Кость кодируется так же, как в документации проекта: `5c`, `1d`, `9b`, `E`, `S`, `W`,
`N`, `Rd`, `Gd`, `Wd`, цветы — `Fl1`..`Fl8`.

| Направление | Сообщение | Поля |
|---|---|---|
| сервер → клиент | `welcome` | место, ветер, номер руки в сессии, сид |
| сервер → клиент | `view` | проекция целиком (после добора, сноса, объявления, конца руки) |
| сервер → клиент | `event` | `draw` / `discard` / `meld` / `flower` / `handEnd`, с костью и местом |
| сервер → клиент | `offer` | какие ходы сейчас допустимы и до какого времени (метка сервера) |
| клиент → сервер | `act` | `kind`, `tile`, `required`, `requestId` |
| сервер → клиент | `reject` | `requestId`, причина (ход не в списке, не ваша очередь, время вышло) |
| сервер → клиент | `settle` | выплаты, очки сессии, таблица после руки |

## 5. Порядок работ

| Шаг | Что делается | Готово, когда |
|---|---|---|
| M0 | `Net/TileNotation.cs`, `Net/ActionCodec.cs`, `Net/SeatView.cs`, `Net/AuthoritativeTable.cs` + `Net/InProcessTransport.cs` | четыре бота играют руку только через сообщения, а проверки в `RulesSelfCheck` подтверждают: проекция не выдаёт чужие кости, подделанный ход отклонён, лог переигрывается в то же состояние |
| M1 | Серверные часы: окна 20 / 10 / 3 ведутся `PlayClock` на сервере, клиент показывает остаток | просроченный ход не зависит от часов клиента |
| M2 | Реальный транспорт: TCP-сокет (десктоп) или WebSocket (веб-сборка), переподключение по снимку + логу | обрыв связи на 10 секунд не ломает руку |
| M3 | Турнирный слой: столы, рассадка, судья | 6+ сессий по схеме 3.5.4 |

M0 можно делать, не решая, какой транспорт будет в игре: он не зависит от сети вообще и сразу
закрывает пункты 4.14 (сохранение сессии) и 4.15 (реплеи) — им нужен тот же лог ходов.

Сделано (2026-11-05): `Replay/SessionLog` пишет лог партии в файл и читает его обратно,
`Replay/ReplayCursor` листает партию внутри игры (`V`), `Replay/SessionRestore` продолжает партию
из файла (`F9`, `MAHJONG_RESUME=1`) — счёт считается заново через `CompleteHand` по переигранным
рукам, часы сессии возвращаются из строки `session|elapsed=…|limit=…`. 4.14 и 4.15 закрыты.
Не переживают сохранение только штрафы судьи: `PenaltyLedger` живёт в сессии и в файл не пишется,
пока в игре нет интерфейса судьи. Тот же файл — готовый формат для переподключения клиента
(снимок = лог + сид, M2).

## 6. Риски

- **Скорость заявок.** Окно заявки — 3 секунды (3.6.7). При задержке в 200 мс это не проблема, но
  сервер должен закрывать окно по своим часам, а не ждать ответа от всех.
- **Спорные руки.** То, что уже решено в `Scoring` (см. `docs/scoring-golden.md`), должно считаться
  на сервере; клиент не должен показывать свой подсчёт даже «для интереса».
- **Подглядывание.** Пока сервер рассылает события вида «игрок 2 снёс кость», всё в порядке. Любая
  попытка прислать клиенту полный `GameState` открывает чужие кости — проекцию нужно держать в одном
  месте и не давать обходных путей.
